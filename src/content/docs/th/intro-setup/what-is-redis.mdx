## In-memory key-value data store

Redis เก็บทุก key และค่าที่เชื่อมโยงโดยตรงใน **RAM** เมื่อแอปพลิเคชันของคุณ set key ข้อมูลจะอยู่ในหน่วยความจำ — ไม่มีการค้นหาดิสก์ ไม่มี page fault ไม่มี overhead ของ file system เมื่ออ่าน key กลับมา คำตอบก็มาจากหน่วยความจำเดิมนั้น นี่คือเหตุผลที่ความหน่วงของ Redis อยู่ต่ำกว่ามิลลิวินาทีอย่างสม่ำเสมอแม้ภายใต้โหลดหนัก

แต่ละค่ามี type Redis ไม่ใช่แค่ที่เก็บ string ธรรมดา — แต่เข้าใจโครงสร้างข้อมูลได้โดยตรง: Strings, Lists, Hashes, Sets, Sorted Sets, Streams และอีกมาก เซิร์ฟเวอร์สามารถทำงานกับโครงสร้างเหล่านั้นแบบ atomic ได้โดยตรง นั่นหมายความว่าคุณสามารถ append ลงใน list, เพิ่มค่า counter, หรือ pop จาก queue ได้โดยไม่ต้องล็อคระดับ application

## Single-threaded event loop

Redis ประมวลผลคำสั่งผ่าน **single-threaded event loop** thread เดียวอ่านคำสั่งจาก network socket, รันให้เสร็จสมบูรณ์, เขียน reply แล้วจึงไปยังคำสั่งถัดไป ไม่มี parallelism ภายใน Redis instance เดียว

การออกแบบนี้มีผลสำคัญสองประการ:

- **ความเร็ว** — ไม่มี context switching, ไม่มี mutex contention, ไม่มี lock overhead event loop ดึงประสิทธิภาพสูงสุดออกจาก core เดียว
- **Thread safety โดยการออกแบบ** — เนื่องจากมีคำสั่งเดียวทำงานในแต่ละครั้ง ทุกคำสั่งจึง atomic โดยปริยาย คุณไม่ต้องกังวลว่า client สองตัวจะทำให้ shared state เสียหายระหว่างการทำงาน

## Data-structure server ไม่ใช่แค่ cache

ประโยคที่ว่า "Redis คือ cache" เป็นเรื่องทั่วไปแต่ไม่ครบถ้วน cache ธรรมดา map key ไปยัง blob ที่ไม่รู้โครงสร้าง Redis map key ไปยัง **โครงสร้างข้อมูลที่หลากหลาย** ที่คุณสามารถจัดการได้ฝั่งเซิร์ฟเวอร์:

| ประเภท | คำอธิบาย |
|------|-------------|
| String | ข้อความ, ตัวเลข, หรือ raw bytes ได้ถึง 512 MB |
| List | ลำดับที่เรียงไว้; push/pop จากทั้งสองด้าน |
| Hash | field-value map ภายใน key เดียว |
| Set | คอลเลกชันของ member ที่ไม่ซ้ำกันแบบไม่มีลำดับ |
| Sorted Set | Set ที่แต่ละ member มี numeric score |
| Stream | บันทึกแบบ append-only ของ entry ที่มี timestamp |

เนื่องจาก operation เกิดขึ้นฝั่งเซิร์ฟเวอร์ คุณจึงหลีกเลี่ยง round trip แทนที่จะ GET → แก้ไข locally → SET คุณใช้ LPUSH หรือ ZINCRBY ใน network call เดียว

## Redis 8 — distribution เดียว ไม่มี module

หลายปีที่ผ่านมา ความสามารถเสริมอยู่ใน **module** ที่ต้องติดตั้งแยก และ "Redis Stack" คือชุดที่รวม module เหล่านั้นมาให้ Redis 8 รวมสองอย่างนี้เข้าด้วยกัน: สิ่งที่เคยเรียกว่า Redis Community Edition ตอนนี้ชื่อ **Redis Open Source** และฟีเจอร์ที่เคยเป็น module ถูกสร้างไว้ในเซิร์ฟเวอร์เลย image ที่คุณจะ pull ในบทถัดไปมีครบแล้ว — ไม่ต้องติดตั้งเพิ่ม ไม่ต้องจับคู่เวอร์ชัน

| มีมาให้ตั้งแต่ Redis 8 | ได้อะไร |
|------|-------------|
| JSON | เก็บและแก้ไข JSON document ในที่เดิมด้วย JSONPath |
| Search and query | secondary index, full-text search และ vector search บน hash หรือ JSON |
| Time series | downsampling, aggregation และ retention สำหรับ sample ที่มี timestamp |
| Probabilistic | Bloom filter, Cuckoo filter, Count-Min sketch, Top-K, t-digest |
| Vector set (beta) | type ของ Redis เองสำหรับ vector similarity search |

Redis 8 ยังเป็นการกระโดดด้านประสิทธิภาพครั้งใหญ่ที่สุดในประวัติของโปรเจกต์ — กว่า 30 การปรับปรุง, ลด latency ของคำสั่งได้ถึง 87% และ replication เร็วขึ้นถึง 18% — พร้อมคำสั่ง hash ใหม่สามตัวที่คุณจะเจอในบท Hashes

<Callout title="คุณยังเรียนทุกอย่างในคอร์สนี้บน Redis 8 ธรรมดาได้">
คอร์สนี้เน้นโครงสร้างข้อมูลหลัก ซึ่งทำงานเหมือนเดิมมาหลายปี ของเสริมด้านบนน่ารู้ไว้เพราะตอนนี้มัน *มีอยู่แล้วโดยค่าเริ่มต้น* — วันที่คุณต้องการ secondary index หรือ vector search คุณไม่ต้องเปลี่ยน deployment เพื่อให้ได้มันมา

## Use case ทั่วไป

| Use case | Redis feature |
|----------|--------------|
| Cache (แคช) | TTL-based expiry บน key ใดก็ได้ |
| Session store (เก็บ session) | Hash ต่อ session ID, อ่านได้เร็ว |
| Task queue (คิวงาน) | LPUSH / BRPOP บน List |
| Leaderboard (ตารางคะแนน) | Sorted Set กับ ZADD / ZRANK |
| Rate limiter (จำกัดอัตราคำขอ) | INCR + EXPIRE บน counter key |
| Pub/Sub messaging (ส่งข้อความ) | PUBLISH / SUBSCRIBE channels |

## ตรวจสอบ type เบื้องต้น

```text
127.0.0.1:6379> PING
PONG
127.0.0.1:6379> SET language "Redis"
OK
127.0.0.1:6379> TYPE language
string
```

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---|---|---|
| เก็บข้อมูลใน RAM (in-memory) | latency ต่ำกว่ามิลลิวินาที อ่าน/เขียนเร็วกว่าดิสก์มาก | ต้นทุน RAM แพงกว่า disk มาก และข้อมูลทั้งหมดต้องพอดีกับหน่วยความจำที่มี |
| Single-threaded event loop | ไม่มี lock contention ทุกคำสั่ง atomic โดยธรรมชาติ debug ง่าย | ใช้ CPU ได้แค่ core เดียวต่อ instance ไม่มี parallelism ภายใน |

## ข้อผิดพลาดที่พบบ่อย

- **คิดว่า Redis คือฐานข้อมูลถาวรโดยอัตโนมัติ** — ค่าเริ่มต้นเน้นความเร็ว ไม่ใช่ durability หากต้องการกันข้อมูลหาย ต้องตั้งค่า persistence (RDB/AOF) เอง
- **ปล่อยให้ dataset โตโดยไม่ตั้ง `maxmemory`** — เพราะทุกอย่างอยู่ใน RAM ถ้าไม่จำกัดขนาดหรือกำหนด eviction policy ไว้ก่อน Redis อาจใช้หน่วยความจำจนเครื่อง OOM
- **เข้าใจผิดว่า single-threaded แปลว่า "ช้า"** — จริง ๆ แล้ว event loop เดี่ยวคือสิ่งที่ทำให้ Redis เร็วเพราะไม่มี context switching แต่ก็หมายความว่าคำสั่งที่หนัก (เช่น `KEYS *` บน dataset ใหญ่) จะบล็อก client อื่นทั้งหมดจนกว่าจะเสร็จ

> 💡 ตัวอย่างจากของจริง
>
> **Stack Overflow** — วาง L1 (local memory)/L2 (Redis) cache ไว้หน้า SQL Server: request จะเช็ก local cache ก่อน แล้วค่อยเช็ก Redis และ query ฐานข้อมูลก็ต่อเมื่อ miss ทั้งสองชั้น ที่สเกลราว 160 พันล้าน operation ต่อเดือนทั้ง fleet ([Stack Overflow: The Architecture – 2016 Edition](https://nickcraver.com/blog/2016/02/17/stack-overflow-the-architecture-2016-edition/), Nick Craver, 2016)
>
> **หลักการทั่วไป** — โปรดักต์ที่มี traffic สูงและอ่านหนักหลายเจ้าวาง in-memory data-structure store ไว้หน้าฐานข้อมูลหลัก เพื่อให้ query แบบ "ข้อมูลล่าสุดของ user นี้" ไม่ต้อง query ฐานข้อมูลทุกครั้ง
