## แนวคิดพื้นฐานของ key-value

Redis คือ key-value store ที่แก่นแท้ ข้อมูลทุกชิ้นอยู่ใต้ **key** หนึ่งตัว key เป็น string เสมอ ส่วน value จะมี **type** — string, list, hash, set, sorted set หรือ stream — และ type นี้เองที่กำหนดว่าใช้คำสั่งอะไรกับ value นั้นได้

ลองนึกภาพเหมือน dictionary ขนาดใหญ่: คุณค้นหา key แล้วได้ value กลับมา คุณยังถามได้ว่า key นั้นมีอยู่ไหม value เป็น type อะไร หรือจะลบมันทิ้งไปเลยก็ได้

## SET และ GET

`SET key value` เก็บค่า `GET key` ดึงค่ากลับมา ถ้า key มีอยู่แล้ว `SET` จะเขียนทับค่าเดิม

```text
127.0.0.1:6379> SET name "Redis"
OK
127.0.0.1:6379> GET name
"Redis"
127.0.0.1:6379> SET score 100
OK
```

## DEL — ลบ key หนึ่งตัวหรือมากกว่า

`DEL key [key ...]` ลบ key หนึ่งตัวหรือมากกว่า และคืนค่าเป็น **จำนวน key ที่ถูกลบจริง** ถ้า key ไม่มีอยู่ Redis จะข้ามไปเฉยๆ และไม่นับรวมในค่าที่คืนกลับมา

```text
127.0.0.1:6379> DEL name
(integer) 1
127.0.0.1:6379> GET name
(nil)
```

## EXISTS — เช็กว่า key มีอยู่หรือไม่

`EXISTS key` คืนค่า `1` ถ้า key มีอยู่ และ `0` ถ้าไม่มี คุณส่ง key ได้หลายตัวพร้อมกัน — ค่าที่คืนกลับมาคือจำนวน key ที่มีอยู่จริง

```text
127.0.0.1:6379> EXISTS name
(integer) 1
127.0.0.1:6379> EXISTS missing
(integer) 0
```

## TYPE — ตรวจสอบ type ของ value

`TYPE key` คืนค่า type ของ value ที่เก็บอยู่ใน key นั้น: `string`, `list`, `hash`, `set`, `zset`, หรือ `stream` และคืนค่า `none` ถ้า key ไม่มีอยู่

```text
127.0.0.1:6379> TYPE name
string
```

## KEYS — แสดง key ตาม pattern

`KEYS pattern` คืนค่า key ทั้งหมดที่ตรงกับ glob pattern `KEYS *` จะจับคู่กับทุก key

```text
127.0.0.1:6379> KEYS *
1) "score"
2) "name"
```

> **คำเตือน:** ห้ามใช้ `KEYS *` ใน production เด็ดขาด Redis เป็น single-threaded — `KEYS` จะบล็อกทั้ง server จนกว่าจะสแกน key ครบทุกตัว บน dataset ใหญ่อาจทำให้แอปพลิเคชันค้างไปหลายวินาที ใช้ `SCAN` แทน เพราะมันวนแบบ batch เล็กๆ ที่ไม่บล็อก

## ตัวอย่างการใช้งานแบบเต็ม

รวมทุกคำสั่งข้างต้นไว้ใน session เดียวต่อเนื่องกัน:

```text
127.0.0.1:6379> SET name "Redis"
OK
127.0.0.1:6379> GET name
"Redis"
127.0.0.1:6379> SET score 100
OK
127.0.0.1:6379> EXISTS name
(integer) 1
127.0.0.1:6379> EXISTS missing
(integer) 0
127.0.0.1:6379> TYPE name
string
127.0.0.1:6379> KEYS *
1) "score"
2) "name"
127.0.0.1:6379> DEL name
(integer) 1
127.0.0.1:6379> GET name
(nil)
```

## แนวปฏิบัติในการตั้งชื่อ key

Key เป็นแค่ string ดังนั้นจะตั้งชื่ออะไรก็ได้ — แต่ชื่อที่มีความหมายจะช่วยให้ debug และ monitor ง่ายขึ้นมาก แนวปฏิบัติมาตรฐานคือ **การแบ่ง namespace ด้วยเครื่องหมายโคลอน**:

| Pattern | ตัวอย่าง |
|---------|---------|
| `object:id` | `user:42` |
| `object:id:field` | `user:42:email` |
| `type:identifier` | `session:abc123` |

รูปแบบนี้ช่วยให้จัดกลุ่ม key ที่เกี่ยวข้องกันได้ง่าย ใช้ glob pattern ได้อย่างปลอดภัย และเข้าใจได้ทันทีว่า key แต่ละตัวเก็บอะไรไว้เมื่อดูผ่านเครื่องมืออย่าง RedisInsight

<Callout title="ทุก value ถูกเก็บไว้ใต้ key — เลือกชื่อ key ที่ชัดเจน">

ชื่อ key ที่มีความหมายจะคุ้มค่ามากตอน debug ระบบจริง `user:42:email` บอกทันทีว่า key นี้เก็บอะไรและเป็นของใคร ในขณะที่ key ที่ไม่มีความหมายอย่าง `e42` บอกอะไรไม่ได้เลย

ใช้ namespace แบบคั่นด้วยโคลอนอย่างสม่ำเสมอทั่วทั้ง codebase หลายทีมใช้รูปแบบอย่าง `object:id:field` และบังคับใช้ผ่านไฟล์ constants กลาง เพื่อไม่ให้การตั้งชื่อ key เพี้ยนไปคนละทาง

</Callout>

## ข้อแลกเปลี่ยน

| ตัวเลือก | Benefit | Cost |
|---|---|---|
| โมเดล key-value แบบไม่มี schema | เริ่มต้นง่าย เก็บอะไรก็ได้ทันทีโดยไม่ต้อง define ตารางล่วงหน้า | ไม่มีการบังคับ schema หรือ type validation ฝั่ง server ผิดพลาดจาก key/value ที่ไม่ตรง type จะรู้ตอน runtime |
| ใช้ `KEYS *` เพื่อดูข้อมูลทั้งหมด | สะดวกเวลาทดลองบน dataset เล็ก ๆ ใน dev | บล็อก event loop จนกว่าจะสแกนครบทุก key ห้ามใช้กับ dataset ใหญ่ใน production |
| เก็บ key แบบไม่ตั้ง TTL | ข้อมูลไม่หายไปเอง เหมาะกับข้อมูลที่ต้องอยู่ถาวร | ถ้าลืมตั้ง expiry สำหรับข้อมูลที่ควรเป็น cache หน่วยความจำจะโตเรื่อย ๆ โดยไม่มีการล้าง |

## ข้อผิดพลาดที่พบบ่อย

- **ใช้ `KEYS *` ใน production เพื่อดู key ทั้งหมด** — คำสั่งนี้บล็อก server จนกว่าจะสแกนเสร็จ บน dataset ใหญ่อาจทำให้ client อื่นค้าง ควรใช้ `SCAN` แทนเมื่อทำงานกับข้อมูลจริง
- **ไม่ตั้ง TTL ให้ key ที่ควรเป็นข้อมูลชั่วคราว** — ถ้าใช้ `SET` เก็บ cache โดยไม่ผูก expiry ไว้เลย หน่วยความจำจะสะสมไปเรื่อย ๆ จนถึงขีดจำกัดของ `maxmemory`
- **ทดสอบคำสั่งผ่าน `redis-cli` แล้วคิดว่าพฤติกรรมจะเหมือนกันทุกอย่างในโค้ดแอปจริง** — client library อาจมี serialization, encoding, หรือ error handling ต่างจากที่เห็นใน CLI ควรทดสอบผ่าน library จริงก่อนขึ้น production ด้วย

> 💡 ตัวอย่างจากของจริง
>
> **Stack Overflow** — ใช้ `SET`/`GET` ง่าย ๆ แบบนี้เป็นส่วนหนึ่งของ L1/L2 cache หน้า SQL Server เพื่อลด query ซ้ำสำหรับหน้าเว็บที่มีคนอ่านพร้อมกันเยอะ ที่สเกลราว 160 พันล้าน operation ต่อเดือน ([Stack Overflow: The Architecture – 2016 Edition](https://nickcraver.com/blog/2016/02/17/stack-overflow-the-architecture-2016-edition/), Nick Craver, 2016)
>
> **หลักการทั่วไป** — แอปที่ต้องอ่านข้อมูลล่าสุดของ user บ่อยๆ (เช่น feed หรือ timeline) มักผูก key อย่าง `user:<id>:timeline` เข้ากับข้อมูลล่าสุดโดยตรง แทนที่จะ query ฐานข้อมูลหลักซ้ำทุกครั้ง
