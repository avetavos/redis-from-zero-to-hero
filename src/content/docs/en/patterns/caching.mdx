The **cache-aside** pattern (also called *lazy loading*) keeps your application in control of what goes into the cache and when. Redis sits in front of your database: if the data is there, great — skip the DB entirely. If not, fetch it from the DB and populate the cache for next time.

## How Cache-aside Works

<Mermaid code={cacheAsideDiagram} title="Cache-aside read flow: check Redis, fall back to the DB on a miss, then write back with a TTL" />

The application owns both reads and writes to the cache. Nothing is preloaded; entries are created on demand and expire automatically via the TTL.

## Reading and Writing a Cache Entry

```text
127.0.0.1:6379> GET cache:user:42
(nil)
127.0.0.1:6379> SET cache:user:42 "{\"name\":\"Ada\",\"email\":\"ada@example.com\"}" EX 300
OK
127.0.0.1:6379> TTL cache:user:42
(integer) 299
127.0.0.1:6379> GET cache:user:42
"{\"name\":\"Ada\",\"email\":\"ada@example.com\"}"
```

`EX 300` sets a 300-second (5-minute) TTL. After that time the key vanishes and the next request will be a cache miss, triggering a fresh DB read.

## Cache Invalidation

When the underlying data changes — a user updates their profile, for example — the cached entry is now stale. The simplest and most reliable fix is to delete the key immediately so the next read fetches fresh data from the DB.

```text
127.0.0.1:6379> SET cache:user:42 "{\"name\":\"Ada updated\"}" EX 300
OK
127.0.0.1:6379> DEL cache:user:42
(integer) 1
127.0.0.1:6379> GET cache:user:42
(nil)
```

## Cache Stampede

A **cache stampede** happens when a popular key expires and dozens (or thousands) of concurrent requests all get a cache miss at the same moment. They all race to the database simultaneously, producing a sudden spike in DB load — the very thing caching was meant to prevent.

Two common mitigations: use `SET ... NX` so only the first writer populates the key and the rest wait, or use **probabilistic early expiration** — a technique that randomly refreshes a key slightly before it expires based on the remaining TTL and an estimated recomputation cost. Both strategies reduce the thundering-herd effect without requiring an external lock service.

<Callout title="Cache-aside + a TTL is the most common Redis use">
Use a short TTL (seconds to minutes) so stale data does not accumulate. Always invalidate (DEL) when the source-of-truth changes.
</Callout>

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Cache-aside | The app controls exactly what enters the cache; the DB is never loaded for data nobody asked for | The first cache miss is slower than normal (query DB + write cache) |
| Write-through | Cache and DB always stay in sync — no stale reads | Every write is slower, since it must write to both before returning |
| Probabilistic early expiration | Reduces thundering herd when a popular key expires | Requires computing a probability per request — extra logic in the app |

## Common mistakes

- **Not setting a TTL on a cache key** — forget `EX` and the data sticks around forever even after the source of truth changes, becoming a permanently stale cache.
- **Letting a cache stampede happen with no protection** — when a popular key expires, thousands of requests can hit the DB at once. Use `SET ... NX` or probabilistic early expiration.
- **Forgetting to invalidate the cache when the underlying data changes** — if you update the DB but don't `DEL` the old cache key, users see stale data until the TTL runs out.

> 💡 Real-world example
>
> **Stack Overflow** placed an L1 (local)/L2 (Redis) cache-aside layer in front of SQL Server to cut repeated queries for heavily-read pages, at a reported scale of roughly 160 billion Redis operations a month ([Stack Overflow: The Architecture – 2016 Edition](https://nickcraver.com/blog/2016/02/17/stack-overflow-the-architecture-2016-edition/), Nick Craver, 2016).
>
> **General pattern** — high-traffic feed products commonly use cache-aside as the core of a timeline/feed cache, keeping the latest items in Redis and falling back to slower storage on a miss.
