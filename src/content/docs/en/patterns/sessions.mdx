## Why Redis for sessions?

Application servers are stateless — sessions must live somewhere external. Redis is a natural fit: it is fast, supports key expiry natively, and its hash type maps cleanly onto a session object with named fields.

## Storing a session as a hash

Each session is stored at key `session:<id>`. Fields such as `userId`, `email`, and `role` map directly to hash fields. An `EXPIRE` sets the idle timeout; refreshing that expiry on every authenticated request gives a sliding TTL.

## Redis CLI demo

```text
127.0.0.1:6379> HSET session:abc123 userId 42 email "ada@example.com" role "admin"
(integer) 3
127.0.0.1:6379> EXPIRE session:abc123 1800
(integer) 1
127.0.0.1:6379> HGETALL session:abc123
1) "userId"
2) "42"
3) "email"
4) "ada@example.com"
5) "role"
6) "admin"
127.0.0.1:6379> HGET session:abc123 role
"admin"
127.0.0.1:6379> EXPIRE session:abc123 1800
(integer) 1
127.0.0.1:6379> TTL session:abc123
(integer) 1799
```

`HSET` with multiple field-value pairs creates the session in one round trip. `HGETALL` returns every field; `HGET` fetches a single field. Calling `EXPIRE` again resets the countdown, implementing the sliding idle timeout.

export const sessionsCode = `HSET session:abc123 userId 42 email "ada@example.com" role "admin"
EXPIRE session:abc123 1800
HGETALL session:abc123
HGET session:abc123 role
EXPIRE session:abc123 1800
TTL session:abc123`;

## Hashes vs. serialised JSON

Storing the session as a single JSON string is tempting but forces you to deserialise the entire blob just to read or change one field. With a hash, `HGET` fetches only the field you need and `HSET` updates only the field that changed — no round-trip of the full session value, and no risk of a write overwriting a concurrent update to a different field.

## Updating a single field

```text
127.0.0.1:6379> HSET session:abc123 role "superadmin"
(integer) 0
127.0.0.1:6379> HGET session:abc123 role
"superadmin"
```

`HSET` returns `0` when it updates an existing field (no new field was added). Only the `role` field is touched; every other field remains unchanged.

export const sessionUpdateCode = `HSET session:abc123 role "superadmin"
HGET session:abc123 role`;

<Callout title="Store sessions as hashes with a sliding TTL">
Call EXPIRE on every authenticated request to keep active sessions alive. When the user logs out, call DEL session:&lt;id&gt; explicitly. Hashes let you read or update individual fields without round-tripping the full session blob.
</Callout>

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| One hash per session | Read/update individual fields without deserializing the whole thing | You must know field names up front — Redis enforces no schema of its own |
| One JSON string | Simple to write and read, naturally holds complex structure | Must deserialize/serialize the whole blob even to change one field |
| Sliding TTL (`EXPIRE` on every request) | An active session never expires mid-use | Requires an extra `EXPIRE` call per request, adding a round trip |

## Common mistakes

- **Forgetting to call `EXPIRE` again on every request** — if the TTL is only set once at login, an active user gets logged out mid-session when that original TTL runs out.
- **Not calling `DEL` on the session key at logout** — if you rely on the TTL alone, a stolen session token keeps working until the TTL expires, even after the user explicitly logged out.
- **Storing sensitive data (like a password) in the session hash** — a session store should hold only what's needed for authorization, not raw credentials.

> 💡 Real-world example
>
> **connect-redis**, a widely used session store for Express/`express-session`, stores each session as a Redis hash the same way this lesson does, with a sliding TTL refreshed per request.
>
> **General pattern** — production systems with large numbers of concurrent users commonly rely on Redis as a session store specifically because key lookups stay fast even at that scale.
