## The appendfsync setting

AOF durability depends on how often Redis flushes the AOF buffer to disk. The `appendfsync` directive controls this with three modes:

- `always`: fsync after every command — zero data loss, lowest throughput
- `everysec`: fsync once per second — at most 1 second of data loss, good balance (recommended)
- `no`: OS decides when to flush — highest throughput, unpredictable data loss

```ini
# Maximum durability — every write fsynced
appendfsync always

# Balance — at most 1 second of data loss (recommended)
appendfsync everysec

# Fastest — OS controls flushing, unpredictable loss
appendfsync no
```

## What you can lose on a crash

| Mode | Max data loss | Throughput |
|------|--------------|------------|
| `always` | 0 commands | Lowest |
| `everysec` | ~1 second | Good |
| `no` | Since last OS flush | Highest |
| RDB only | Since last snapshot | Highest |

## Combining persistence with replication

Running replicas does NOT replace persistence. A replica that crashes and restarts will reload from its own persistence files (or sync from primary). Best practice: enable persistence on replicas independently, not just on the primary.

```text
127.0.0.1:6379> CONFIG GET appendfsync
1) "appendfsync"
2) "everysec"
127.0.0.1:6379> CONFIG SET appendfsync always
OK
127.0.0.1:6379> CONFIG GET appendfsync
1) "appendfsync"
2) "always"
```

<Callout title="appendfsync everysec — the common balance">

Most production deployments use `appendfsync everysec`. You get AOF durability with at most 1 second of data loss on crash, and throughput stays high. Use `always` only when zero data loss is a hard requirement.

</Callout>

<Callout title="AOF is off by default, and modern AOF is a directory, not one file">

`appendonly` defaults to `no` — a fresh Redis instance only persists via RDB snapshots unless you explicitly `CONFIG SET appendonly yes` (or set it in `redis.conf`). Since Redis 7.0, enabling AOF creates a multi-part layout under a directory (`appenddirname`, default `appendonlydir`): a base file, one or more incremental files, and a manifest that ties them together — this is what makes background rewrites cheaper than the old single growing file.

</Callout>

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| `appendfsync always` | No data loss even on crash | `fsync()` on every command, the lowest throughput of the three modes |
| `appendfsync everysec` | Balances durability and throughput — fits most production workloads | Up to ~1 second of data loss on crash |
| `appendfsync no` | Highest throughput, no fsync overhead | The OS decides when to flush; data loss is unpredictable if the disk hasn't flushed yet |

## Common mistakes

- **Assuming a replica replaces the need for persistence** — a replica that crashes and restarts still has to reload from its own persistence files (or resync from the primary). Enable persistence on replicas independently rather than relying on the primary alone.
- **Using `appendfsync no` on a system that cannot tolerate data loss** — this mode gives the highest throughput but lets the OS decide when to flush; a crash before that flush loses everything since the last one.
- **Never testing recovery after a real crash** — a correct `appendfsync` setting is useless if you've never actually `kill -9`'d the process and confirmed Redis restarts and reloads the data you expected.
