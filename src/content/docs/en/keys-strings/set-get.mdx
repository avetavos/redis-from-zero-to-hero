## SET and GET — the core of Redis strings

`SET key value` stores a string. `GET key` retrieves it. If the key already exists, `SET` **overwrites** it unconditionally (unless you add a condition flag).

```text
127.0.0.1:6379> SET city "Bangkok"
OK
127.0.0.1:6379> GET city
"Bangkok"
127.0.0.1:6379> SET city "Chiang Mai"
OK
127.0.0.1:6379> GET city
"Chiang Mai"
```

## SET options

`SET` supports several options in one command:

| Option | Meaning |
|--------|---------|
| `EX seconds` | Set expiration in seconds |
| `PX milliseconds` | Set expiration in milliseconds |
| `EXAT unix-time-seconds` | Expire at a Unix timestamp (seconds) |
| `PXAT unix-time-ms` | Expire at a Unix timestamp (milliseconds) |
| `NX` | Only set if the key does **not** exist |
| `XX` | Only set if the key **does** exist |
| `GET` | Return the old value before overwriting |
| `KEEPTTL` | Retain the existing TTL instead of resetting it |

```text
127.0.0.1:6379> SET token "abc123" EX 60
OK
127.0.0.1:6379> TTL token
(integer) 59
127.0.0.1:6379> SET counter 0 NX
OK
127.0.0.1:6379> SET counter 99 NX
(nil)
127.0.0.1:6379> GET counter
"0"
127.0.0.1:6379> SET city "Phuket" GET
"Chiang Mai"
127.0.0.1:6379> GET city
"Phuket"
```

export const setOptionsCode = `SET token "abc123" EX 60
TTL token
SET counter 0 NX
SET counter 99 NX
GET counter
SET city "Phuket" GET
GET city`;

## SETEX and SETNX

These are older convenience aliases — `SET` with `EX` or `NX` is preferred in modern Redis, but you will still see them in legacy code:

```text
127.0.0.1:6379> SETEX session:user1 3600 "token-xyz"
OK
127.0.0.1:6379> TTL session:user1
(integer) 3599
127.0.0.1:6379> SETNX lock:job1 "worker-A"
(integer) 1
127.0.0.1:6379> SETNX lock:job1 "worker-B"
(integer) 0
127.0.0.1:6379> GET lock:job1
"worker-A"
```

export const legacyCode = `SETEX session:user1 3600 "token-xyz"
TTL session:user1
SETNX lock:job1 "worker-A"
SETNX lock:job1 "worker-B"
GET lock:job1`;

## MSET and MGET — batch operations

Set or get many keys in a single round-trip. This is significantly faster than individual commands when you need multiple keys at once.

```text
127.0.0.1:6379> MSET user:1:name "Ada" user:1:lang "Python" user:2:name "Bob" user:2:lang "Go"
OK
127.0.0.1:6379> MGET user:1:name user:1:lang user:2:name user:2:lang
1) "Ada"
2) "Python"
3) "Bob"
4) "Go"
127.0.0.1:6379> MGET user:1:name user:99:name
1) "Ada"
2) (nil)
```

export const msetCode = `MSET user:1:name "Ada" user:1:lang "Python" user:2:name "Bob" user:2:lang "Go"
MGET user:1:name user:1:lang user:2:name user:2:lang
MGET user:1:name user:99:name`;

## APPEND and STRLEN

`APPEND` adds to the end of an existing string value (or creates the key if absent). `STRLEN` returns the byte length of the value.

```text
127.0.0.1:6379> SET log "2024-01-01 boot"
OK
127.0.0.1:6379> APPEND log " | 2024-01-01 ready"
(integer) 34
127.0.0.1:6379> GET log
"2024-01-01 boot | 2024-01-01 ready"
127.0.0.1:6379> STRLEN log
(integer) 34
```

export const appendCode = `SET log "2024-01-01 boot"
APPEND log " | 2024-01-01 ready"
GET log
STRLEN log`;

<Callout title="SET key val NX — the basis for distributed locks">

`SET key value NX` sets the key **only if it does not already exist**. It returns `OK` on success and `(nil)` if the key was already there. This atomicity makes it the building block for simple distributed locks:

```text
SET lock:resource "worker-id" NX EX 30
```

If two workers race, only one gets `OK`. The `EX 30` ensures the lock auto-releases after 30 seconds even if the holder crashes.

</Callout>

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| `SET key val NX` (conditional set) | Atomic check-then-set in one command; enough for a basic lock/dedup | No ownership token built in — you must design that yourself for safe unlocking |
| `MSET`/`MGET` (batch operations) | Fewer round trips when setting/getting several keys at once | Not atomic across different key types like a full transaction (use `MULTI`/`EXEC` for real isolation) |
| Plain unconditional `SET key val` | Simple, overwrites immediately with no pre-check | Risk of accidentally overwriting another client's data if key names are not unique enough |

## Common mistakes

- **Using a plain `SET` when you meant "set only if it doesn't exist"** — forgetting `NX` silently overwrites existing data. Use `SET key val NX` when the logic needs an atomic check-then-set.
- **Forgetting that a plain `SET` resets a key's existing TTL** — if you want to keep the existing expiry while updating the value, add `KEEPTTL`; otherwise the key becomes persistent again.
- **Mixing the legacy `SETNX`/`SETEX` commands with `SET ... NX/EX` in the same codebase** — this produces inconsistent style. Standardize on `SET` with options, as recommended since Redis 7+.

> 💡 Real-world example
>
> **Stripe's public API** documents an idempotency-key algorithm: a client sends an `Idempotency-Key` header, the server saves the result of the first request under that key, and replays the same result for any retry with the same key within 24 hours ([Idempotent requests](https://docs.stripe.com/api/idempotent_requests), Stripe Docs). Implementing that same guarantee in Redis with `SET key val NX EX <ttl>` is a Stripe-style idempotency pattern — the key succeeds exactly once, so only the request that set it is the one that actually runs.
>
> **General pattern** — feature-flag and config caches often use `MSET`/`MGET` to fetch several config values in a single command, instead of firing a separate `GET` per key and paying the network round-trip for each one.
