## What is pipelining?

Every Redis command involves a round-trip: the client sends the command, waits for the reply, then sends the next command. Over a network with even modest latency, this adds up quickly.

**Pipelining** lets the client send a batch of commands in one write, without waiting for each individual reply. The server processes them in order and returns all replies together. The result is a single round-trip instead of N round-trips.

```text
# Without pipelining: 3 round-trips
127.0.0.1:6379> SET a 1
OK
127.0.0.1:6379> SET b 2
OK
127.0.0.1:6379> SET c 3
OK

# With pipelining: 1 round-trip, same results
```

Most Redis client libraries expose pipelining directly. In Node.js (ioredis), for example:

```js
const pipeline = redis.pipeline();
pipeline.set('a', 1);
pipeline.set('b', 2);
pipeline.set('c', 3);
const results = await pipeline.exec();
```

## redis-cli --pipe mode

The `redis-cli` tool ships with a `--pipe` flag that accepts Redis protocol (RESP) on stdin and sends it as a pipeline:

```bash
# Generate RESP inline and pipe it to Redis
printf "*3\r\n\$3\r\nSET\r\n\$2\r\nk1\r\n\$5\r\nhello\r\n*3\r\n\$3\r\nSET\r\n\$2\r\nk2\r\n\$5\r\nworld\r\n" \
  | redis-cli --pipe
```

This is useful for bulk imports: tools like `redis-cli --pipe` can load millions of keys in seconds by sending large batches over a single connection.

You can also generate a text file of commands and pipe them:

```bash
# commands.txt contains one redis-cli command per line
cat commands.txt | redis-cli --pipe
```

## Pipelines vs transactions

Pipelines and transactions are often confused. The table below clarifies the difference:

| Feature | Pipeline | Transaction (`MULTI`/`EXEC`) |
|---------|----------|------------------------------|
| Round-trips | One (or few) | One per command + EXEC |
| Atomicity | No — other clients can interleave | Yes — no interruption |
| Rollback | No | No |
| Use case | Throughput / bulk load | Safe grouped write |

A pipeline is a **network optimization**. A transaction is an **atomicity guarantee**. You can combine them: many client libraries let you send a `MULTI`/`EXEC` block inside a pipeline to get both benefits.

A pipeline cuts the number of network round-trips, which can dramatically increase throughput for bulk writes or reads. ## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Pipeline (batch several commands in one request) | Cuts network round-trips down to nearly one, a big throughput win for bulk operations | No atomicity — other clients can interleave commands between the ones in your pipeline |
| `redis-cli --pipe` for bulk import | Loads millions of keys in seconds over a single connection | You must build the RESP protocol yourself or use a command file, harder to debug than one command at a time |
| Wrapping `MULTI`/`EXEC` inside a pipeline | Get both fewer round-trips and an atomicity guarantee | More client-side code complexity — you need to understand both concepts together |

## Common mistakes

- **Assuming a pipeline gives atomicity like a transaction** — a pipeline is only a network optimization that batches commands into one write. Other clients can still run their own commands in between. Wrap it in `MULTI`/`EXEC` if you need atomicity.
- **Sending an overly large pipeline in one go** — a very large batch can temporarily balloon memory buffers on both the client and server. Split it into reasonably sized batches (e.g. a few thousand commands per pipeline).
- **Not checking each command's result within the pipeline** — a pipeline returns an array of results in command order. If one command fails partway through, the others still run. You must loop through the results checking for errors yourself, not assume the whole batch succeeded.

> 💡 Real-world example
>
> **General pattern** — bulk data import jobs commonly use `redis-cli --pipe` or client-library pipelining to load seed data or migrate millions of keys into Redis, cutting round-trips from millions down to a handful of batches. Systems that write a high volume of events per second commonly batch `SET`/`INCR`/`ZADD` commands into a pipeline to reach the throughput needed for high-volume traffic.
