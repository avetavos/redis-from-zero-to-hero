## How Pub/Sub works

Redis Pub/Sub follows the classic publish-subscribe pattern:

1. A client calls `SUBSCRIBE channel` and enters listening mode. It can no longer issue regular commands — it only receives push messages from Redis.
2. Any other client calls `PUBLISH channel message`. Redis immediately forwards that message to every currently connected subscriber of that channel.
3. The message is never stored. If no subscribers are connected, the message is silently discarded. If a subscriber was connected ten seconds ago but disconnected, it gets nothing.

Each channel is just a name — Redis creates and destroys channels implicitly as subscribers come and go. There is no need to create a channel before publishing to it.

## SUBSCRIBE and PUBLISH — two-terminal demo

The interaction below requires two separate `redis-cli` sessions running at the same time. Start Terminal 1 first, then send from Terminal 2.

```text
# Terminal 1 — subscriber
127.0.0.1:6379> SUBSCRIBE news
Reading messages... (press Ctrl-C to quit or any command to unsubscribe)
1) "subscribe"
2) "news"
3) (integer) 1

# Terminal 2 — publisher (in a second redis-cli session)
127.0.0.1:6379> PUBLISH news "Breaking: Redis is fast"
(integer) 1

# Back in Terminal 1 — message arrives automatically
1) "message"
2) "news"
3) "Breaking: Redis is fast"
```

The confirmation message Redis sends back to the subscriber on `SUBSCRIBE` has three parts:

| Part | Value | Meaning |
|---|---|---|
| 1 | `"subscribe"` | Event type |
| 2 | `"news"` | Channel name |
| 3 | `(integer) 1` | Total channels this client is now subscribed to |

When a published message arrives, it also has three parts: the event type `"message"`, the channel name, and the payload.

The integer returned by `PUBLISH` is the number of subscribers who received the message. A return value of `0` means nobody was listening.

## UNSUBSCRIBE

To leave a channel, a subscribed client sends `UNSUBSCRIBE`. You can name a specific channel or omit the channel name to unsubscribe from all channels at once.

```text
# Unsubscribe from one channel
127.0.0.1:6379> UNSUBSCRIBE news
1) "unsubscribe"
2) "news"
3) (integer) 0

# Unsubscribe from all channels (no argument)
127.0.0.1:6379> UNSUBSCRIBE
1) "unsubscribe"
2) (nil)
3) (integer) 0
```

Once the subscription count drops to `0`, the client exits listening mode and can issue normal commands again.

## SUBSCRIBE to multiple channels

A single `SUBSCRIBE` call accepts any number of channel names. The client receives messages from all of them on the same connection.

```text
127.0.0.1:6379> SUBSCRIBE sports weather finance
1) "subscribe"
2) "sports"
3) (integer) 1
1) "subscribe"
2) "weather"
3) (integer) 2
1) "subscribe"
2) "finance"
3) (integer) 3
```

Redis sends one confirmation reply per channel. The third field increments as each subscription is added, giving you the running total.

<Callout title="Pub/Sub is fire-and-forget — offline subscribers miss messages">

There is no buffer, no retry, and no history. The moment `PUBLISH` returns, the message is gone. A subscriber that was offline for a single millisecond during that window will never see it. If your application cannot accept message loss, use Redis Streams instead.

</Callout>

<Callout title="Sharded Pub/Sub — SPUBLISH / SSUBSCRIBE (Redis 7.0+)">

In a Redis Cluster, a plain `PUBLISH` message has to be re-broadcast to every node so it reaches subscribers regardless of which shard they're connected to — expensive at scale. Since Redis 7.0, `SPUBLISH channel message` and `SSUBSCRIBE channel` restrict delivery to the shard that owns the channel's hash slot, so message traffic scales with your cluster instead of hitting every node. Outside a cluster, sharded and regular Pub/Sub behave the same; use sharded Pub/Sub when you are running Cluster mode and want Pub/Sub load spread across shards.

</Callout>

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Fire-and-forget Pub/Sub | Very low latency, no overhead from writing a log to disk | A message is gone forever if no subscriber was connected at that moment — no replay |
| Subscribing to multiple channels on one connection | Fewer connections to open against Redis | The connection is in listening mode entirely — you cannot run other commands on it until you unsubscribe |

## Common mistakes

- **Using Pub/Sub for messages that must be guaranteed to arrive** — like order confirmations or payment events. If a consumer is briefly offline, the message is gone. Use Streams instead when a message cannot be lost.
- **Forgetting that a subscribed client cannot run regular commands** — the connection enters listening mode immediately; you cannot call `GET`/`SET` on that same connection. Open a separate connection to publish.
- **Not checking the value `PUBLISH` returns** — a `0` means no subscriber received the message. Ignoring this return value means you won't notice messages silently disappearing.

> 💡 Real-world example
>
> **General pattern** — chat apps commonly use Pub/Sub to send a "typing..." indicator, since that data goes stale quickly and it's fine for it to be lost if a subscriber misses it. Real-time dashboards use the same mechanism to broadcast a metric that updates every second to many open browser tabs, without worrying about a missed update since the next one arrives so soon.
